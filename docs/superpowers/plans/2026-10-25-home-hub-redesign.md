# PBB 홈 앱 허브 개편 계획서

> 실행 지침: `executing-plans`에 따라 한 구현 담당자가 순차 실행한다. 프로젝트 AGENTS.md가 스킬 기본 절차보다 우선한다. 단계별 커밋·작업트리·실행 방식 선택을 강제하지 않는다. 이 문서는 계획이며 구현 승인을 대신하지 않는다.

**Goal:** 권한에 따라 달라지고 앞으로 늘어날 앱을 쉽게 비교하고, 사용하던 앱으로 빠르게 돌아가는 홈을 만든다.

**Architecture:** 기존 `getNavHobbies(isDev)`와 라우팅을 유지하고 홈을 단일 앱 그리드로 변경한다. 홈 전용 카드·최근 사용 영역·스타일을 분리하고, 최근 사용 기록은 계정별 브라우저 저장소에 앱 ID만 저장한다. 서버 API와 인증·인가 로직은 변경하지 않는다.

**Tech Stack:** React 19, TypeScript, React Router 7, Zustand 5, 기존 CSS 변수, Vitest/Testing Library, Playwright.

**Spec:** 이 문서의 화면·상태·수용 기준이 통합 명세다. 2026-10-25 대화에서 확인한 데스크톱/모바일 이미지 시안을 참고한다. 이미지의 내부 화면은 생성 예시이며 실제 앱 기능이나 디자인 변경 명세가 아니다.

## 1. 현황과 범위

- 공개 앱은 Veveno, Sranko, Tempori다. 현재 일반 로그인도 3개이며 DEV 권한에서 6PICK, Dieta가 추가된다. 로그인 자체가 5개 노출 조건은 아니다.
- `HomePage.tsx`의 앞 2개 featured / 나머지 grid 분리를 없앤다. 앱 수를 3개나 5개로 하드코딩하지 않는다.
- 상단 소개 축소, 카드 통일, 최근 사용, 홈 헤더 탐색 개선, 라이트·다크 및 모바일 대응을 포함한다.
- 검색, 카테고리 필터, 즐겨찾기, 앱 순서 사용자 설정, 서버 기록 동기화는 이번 범위에서 제외한다. 앱이 더 늘어 탐색 비용이 확인될 때 추가한다.
- 앱 내부 페이지, 기존 직접 실행 경로, 소개 페이지, 권한 정책, 실제 환경 파일은 변경하지 않는다. 환경변수 추가는 없다.

## 2. 화면 설계

### 헤더

- 홈에서는 `PBB 로고 / 앱 / 테마 / 계정`으로 단순화한다. 앱 항목은 홈의 전체 앱 영역으로 이동한다.
- 미로그인에서는 계정 대신 로그인 버튼과 보조 가입 링크를 표시한다. 본문의 로그인·가입 중복 버튼은 제거한다.
- 로그인 시 기존 닉네임·설정·로그아웃 기능을 유지한다. 시안의 임의 P 아바타를 필수로 도입하지 않는다.
- 홈 모바일 메뉴에는 현재 권한으로 볼 수 있는 앱 이름과 기능명을 함께 표시한다.
- 홈 전용 분기와 스타일을 사용하여 다른 앱의 헤더, Tempori 집중 화면, 팝업 도구 화면은 유지한다.
- 본문 바로가기, 메뉴의 expanded 상태, 키보드 탐색, Escape 닫기 및 트리거 포커스 복귀를 지원한다. 단순 펼침 링크 목록에 불필요한 ARIA menu 역할을 부여하지 않는다.

### 소개와 최근 사용

- 제목: **일상에 필요한 도구, 한곳에.**
- 설명: **하고 싶은 일을 고르고 바로 시작하세요.**
- 거대한 홍보 영역 대신 짧은 소개로 구성한다. 모바일 제목은 자연스러운 두 줄까지 허용한다.
- 최근 사용은 로그인하고 유효한 기록이 있을 때만 표시한다. 최대 2개, 최신 사용 우선, 중복 없음. 빈 안내 상자로 공간을 차지하지 않는다.
- 최근 사용은 앱명·기능명·작은 아이콘 또는 이니셜로 표시하며 실행 경로로 연결한다.

### 전체 앱

- 제목은 `전체 앱`, 개수는 현재 권한으로 필터링된 배열 길이로 표시한다.
- 1024px 이상: 3열. 768~1023px: 2열. 767px 이하: 가로형 카드의 1열 목록.
- 공개 3개, DEV 5개, 향후 더 많은 앱 모두 동일한 단일 그리드를 사용한다. 마지막 행의 빈 칸은 채우지 않는다.
- 전체 앱 순서는 기존 데이터 순서를 유지한다. 최근 사용 때문에 전체 목록 위치가 바뀌지 않는다.
- 데스크톱: 제품 이미지 → 기능 제목 → 브랜드 → 짧은 설명 → 열기·소개. 이미지 영역 비율과 버튼 정렬을 통일한다.
- 모바일: 작은 제품 이미지/이니셜 + 기능 제목·브랜드·짧은 설명 + 실행 버튼. 소개 링크는 보조 위치에 유지한다. 좁은 폭에서는 버튼을 다음 줄로 내려도 설명을 삭제하지 않는다.
- 제목·설명은 긴 문자열을 고려하고 카드 내부 넘침을 방지한다. 주 버튼 글자는 14~16px, 터치 영역은 최소 44×44px로 잡는다.
- 화면의 버튼 문구는 `열기`, 접근성 이름은 `Veveno 열기`처럼 앱별로 구분한다. 이동은 Link를 사용하며 중첩 링크/버튼을 만들지 않는다.
- 이미지 전체를 클릭할 수 있는 카드로 만들지 않는다. 실행과 소개라는 두 목적지를 명확히 분리한다.

| 앱 | 기능 제목 | 홈 설명 | 색상 방향 |
| --- | --- | --- | --- |
| Veveno | 가게 관리 | 메뉴·재고·근무를 한곳에서 | 크림 |
| Sranko | 디지털 옷장 | 옷과 코디를 차곡차곡 | 피치 |
| Tempori | 악보 연습 | 악보와 메트로놈으로 연습 | 기존 네이비 계열, 밝은 배경에서는 옅은 보라 |
| 6PICK | 로또 번호 분석 | 번호와 패턴을 살펴보세요 | 라일락 |
| Dieta | 체중 코칭 | 체중·식사·활동을 기록하세요 | 민트 |

- 공통 subtitle/description을 덮어써 다른 랜딩의 문구를 바꾸지 않는다. 선택적인 `homeTitle`, `homeDescription`을 데이터에 추가하며 없으면 기존 값을 사용한다.
- 실제 기존 productImage/productImageDark를 사용한다. 생성 이미지 속 가상의 앱 화면은 제품 이미지로 채택하지 않는다.
- 라이트·다크 모두 기존 디자인 토큰을 우선한다. 홈 전용 색상은 홈 범위에만 선언한다.
- 하단은 작은 PBB와 `일상을 위한 작은 도구들` 문구만 표시한다. 존재하지 않는 문의/정책 링크를 추가하지 않는다.

## 3. 최근 사용 동작과 인터페이스

- 신규 `frontend/src/features/home/homeRecentStorage.ts`: `readRecentAppIds(userId: string): string[]`, `recordRecentApp(userId: string, appId: string): string[]`, `getVisibleRecentApps(ids: readonly string[], visibleApps: readonly HobbyApp[], limit = 2): HobbyApp[]`.
- 저장 키: `pbb:recent-apps:v1:${encodeURIComponent(userId)}`. 값은 `{ version: 1, appIds: string[] }`이며 최대 20개 ID만 보관한다. 토큰·이메일·닉네임·앱 내부 데이터는 저장하지 않는다.
- 로그인 토큰과 안정적인 userId가 모두 있을 때만 사용한다. userId가 없으면 이메일 등으로 대체하지 않고 기록·표시를 생략한다.
- 읽을 때 JSON 구조·버전을 검증한다. 잘못된 값, 저장 차단, 용량 오류는 홈 렌더링이나 앱 이동을 방해하지 않아야 한다.
- 렌더링 전에 항상 현재 `getNavHobbies` 결과와 교집합을 구한다. 로그아웃, 계정 교체, 권한 감소 시 이전 사용자/권한의 앱을 잠깐이라도 표시하지 않는다.
- 신규 `RecentAppTracker.tsx`에서 현재 pathname을 카탈로그의 `usagePaths`(실제 등록된 실행 경로 패턴)와 비교한다. 매장 상세·코디·악보 등 직접 진입도 포함한다. 패턴은 전체 경로를 일치시키고 `:id`는 한 경로 구간만 허용한다. usagePaths가 없는 새 앱은 startPath 정확 일치를 사용한다. 소개·미등록 경로는 기록하지 않는다. 이는 계획 리뷰에서 발견한 직접 진입 누락을 반영한 수정이다.
- AppShell에 렌더링 없는 추적기를 연결한다. 인증 초기화 후 로그인·userId·가시성·실행 경로가 모두 유효할 때만 기록한다. 이를 인가 성공 판정으로 사용하지 않는다.
- StrictMode 중복 effect, 동일 앱 내부 이동은 중복 ID를 만들지 않는다. 사용자나 pathname 변경 시 다시 평가한다.
- 기록은 같은 브라우저에만 남는다. 서버/기기간 동기화, 탭 사이의 즉각적인 동기화는 제공하지 않는다. 홈 재진입 시 다시 읽는다.

## 5. 단계별 실행 계획

### 단계 1 — 기존 규칙 고정과 최근 사용

- [ ] 테스트에 공개/일반 사용자 3개, DEV 5개 가시성을 고정한다. 향후 앱 수 테스트는 별도 fixture로 6개·7개를 제공하며 실제 공개 데이터에 가짜 앱을 넣지 않는다.
- [ ] 최근 기록의 최신순·중복 제거·최대 20개·표시 최대 2개·계정 분리·권한 필터·손상/차단 저장소를 검증하는 실패 테스트를 작성한다.
- [ ] 앞서 정의한 저장 인터페이스를 구현하고 테스트한다.
- [ ] 추적기의 소개 제외, 실행 경로 일치, 비슷한 접두어 거부, 미로그인/누락 userId 미기록, 동일 effect 반복을 테스트하고 구현한다.

### 단계 2 — 홈 정보 구조와 카드

- [ ] frontend-design 스킬과 기존 디자인 토큰을 확인해 이미지 시안을 실제 반응형 규격으로 옮긴다.
- [ ] HomePage 테스트로 3개/5개 노출, 실제 링크 목적지, 빈 최근 영역 미출력, 계정 전환과 권한 감소 시 이전 항목 미노출을 고정한다.
- [ ] 홈 전용 문구 필드와 HomeAppCard, RecentAppsSection을 구현한다. 앱 카드의 props는 `{ app: HobbyApp }`로 하고 크기별 featured 플래그를 만들지 않는다.
- [ ] HomePage의 두 목록을 하나로 통합하고 home.css로 3/2/1열, 가로형 모바일 카드, 다크 모드와 포커스 표시를 구현한다.

### 단계 3 — 헤더와 연결

- [ ] 홈에서만 헤더 탐색을 간결화하고 기존 로그인·설정·로그아웃 동작을 유지한다.
- [ ] 최근 사용 추적기를 연결하고 홈 복귀 시 최신 기록을 반영한다.
- [ ] 모바일 메뉴 열기/닫기, 링크 이동, Escape와 포커스 복귀, 앱 목록 앵커의 sticky 헤더 간격을 확인한다.
- [ ] 다른 앱의 헤더·집중 화면·팝업 경로의 회귀를 확인한다.

### 단계 4 — 리뷰와 재검증

- [ ] web-design-guidelines로 구현 후 UI를 재검토하고 관련 발견사항을 수정한다.
- [ ] 요청된 코드 리뷰 절차에 따라 실제 diff와 기존 미커밋 변경을 구분해 검토한다. 독립 리뷰가 가능/허용되면 사용하고, 그렇지 않으면 자체 리뷰임을 보고한다.
- [ ] 수정 영향 범위의 테스트를 다시 실행하고 결과·미검증 범위를 기록한다. 구현 계획과 실제 결과가 다르면 이 문서를 갱신한다.

## 6. 수용 기준과 검증

- 공개/일반 사용자 3개, DEV 5개를 기존 정책대로 표시하며 제한된 앱이 최근 사용/메뉴로 새어 나오지 않는다.
- 앱 fixture 6개·7개도 순서대로 같은 카드 규격으로 확장된다. 전체 앱 수는 동적으로 계산된다.
- 360·390·768·1024·1440px에서 가로 넘침, 설명 소실, 버튼 겹침이 없다. 라이트·다크 양쪽을 확인한다.
- 모바일에서도 기능 설명과 소개 링크를 사용할 수 있고 실행 버튼의 이름/터치 영역/포커스를 확인할 수 있다.
- 긴 앱명·설명, 긴 닉네임, 200% 확대, 이미지 실패, 빈 가시 목록을 확인한다. 이미지 실패 시 이니셜 대체, 빈 가시 목록은 `사용 가능한 앱이 없습니다.` 안내를 제공한다.
- 최근 사용은 기록 없음/1개/여러 개, 사용자 A→B, DEV→일반, 로그아웃, 저장소 오류를 확인한다. 오래된 앱 ID는 표시되지 않는다.
- 기존 직접 실행과 소개 링크를 유지하며 홈 디자인 변경 때문에 인증 리다이렉트나 앱 기능이 바뀌지 않는다.

실행 가능한 개발 환경에서 사용할 명령 (frontend 기준):

```sh
node --test tests/homeRecentApps.node-test.mjs
npm run test -- src/data/hobbies.test.ts src/features/home/RecentAppTracker.test.tsx src/pages/HomePage.test.tsx src/components/AppShell.home.test.tsx
npm run lint
npm run build
npm run test:e2e -- e2e/home.spec.ts
```

**현재 환경 제한:** node_modules, dist, 테스트 산출물 등이 ignore/접근 제한 대상이므로 위 명령을 현재 채팅에서 그대로 실행할 수 있다고 가정하지 않는다. 실제 .env를 자동 로드하는 Vite 실행도 금지한다. 경로·의존성·출력·환경 파일 접근을 먼저 확인하고, 제한을 만족하지 못하면 사용자가 로컬에서 실행해야 하는 검증으로 남긴다. 우회 복사·권한 약화·제한된 의존성 실행은 하지 않는다. 공개 사이트 확인은 기존 화면의 근거일 뿐 변경 코드 검증을 대신하지 않는다.

## 7. 리뷰 초점·리스크·완료 보고

1. 계정 전환/로그아웃/권한 감소: 단계 1 저장 필터와 단계 2 렌더링 테스트로 이전 기록 노출을 차단한다.
2. 저장소 손상·비활성화: 단계 1에서 안전한 빈 결과와 이동 유지 동작을 검증한다.
3. 경로 접두어 충돌·소개 방문·인증 초기화: 단계 1 추적기 테스트에서 기록 조건을 고정한다.
4. 앱 수 증가·긴 문구·작은 화면: 단계 2 fixture와 단계 4 브라우저 검증으로 넘침과 정보 손실을 확인한다.
5. 공통 CSS/헤더 공유: 홈 범위로 변경을 제한하고 단계 3·4에서 기존 앱 랜딩·집중 화면·팝업 회귀를 확인한다.

완료 시 변경 파일, 실제 수행한 테스트/빌드/브라우저 확인, 남은 제한, 자체/독립 리뷰 여부를 구분해 보고한다. 계획은 현재 에이전트가 작성한 뒤 gpt-6-astra/high 독립 계획 리뷰를 반영했다. 구현도 동일 설정의 독립 코드 리뷰를 받았다. 부모 모델/추론 설정은 실행 결과에서 확인되지 않아 미확인으로 기록하며, 선호 모델이 단계를 수행했다고 주장하지 않는다.

## 8. 구현 결과 (2026-10-25)

- 홈·모바일 카드·헤더·최근 사용 기능을 구현했다. 권한별 기존 노출과 직접 실행/소개 경로는 유지했다.
- 독립 계획 리뷰에 따라 usagePaths 기반의 실제 내부 경로 추적과 홈 전용 이미지 오류 대체, 헤더 테스트를 추가했다.
- 독립 코드 리뷰의 이미지 테스트 선택자 오류를 수정했다. 경로 대소문자 회귀는 실패를 확인한 뒤 수정해 Node 테스트 12/12 통과를 확인했다.
- 기존 후반 모바일 app-shell 여백 규칙이 홈을 덮어쓰지 않도록 홈 전용 클래스에 한정하여 padding을 지정했다.

- 실제 CSS와 이미지로 정적 검토 fixture를 만들었으나 브라우저 file URL/소스 경로 접근 제한과 로컬 서버 EPERM으로 표시하지 못했다. 변경 후 화면·반응형·계정 UI의 브라우저 검증은 미완료다. 임시 fixture는 저장소에서 제거했다.

- 위 체크리스트는 실행 검증까지 필요한 항목을 미완료로 유지한다. 문서의 구현 결과가 현재 작업 상태를 구분한다.
