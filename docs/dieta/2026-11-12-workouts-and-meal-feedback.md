# Dieta 운동 목록과 식사 평가 구현 계획

## 목표와 인수 조건

같은 날 웨이트와 러닝을 따로 기록하고, 하루와 끼니를 열었을 때 각각 다른 질문에 답한다. 하루 요약은 “오늘 기록에서 무엇이 두드러졌나”, 끼니 평가는 “이 끼니에서 어떤 음식이나 분량이 영향을 주었나”를 설명한다. 분석 호출은 기존 기본 1회 + 새 음식 입력 후 추가 1회 범위를 유지한다.

## 1. 하루 운동을 목록으로 기록

- [ ] 활동 탭의 걷기 영역에는 날짜별 걸음 수와 걷기 추정 kcal를 둔다. 운동 영역에는 개별 행과 ‘운동 추가’를 둔다. 새 운동에는 이름을 입력하고 시간(분)과 운동 열량(kcal)은 각각 선택 입력한다. 운동 행에서 수정·삭제하며 빈 초안은 저장하지 않는다.
- [ ] 기존 일별 활동 행은 홈·주간 통계·분석이 읽는 합계로 유지한다. 기존 dieta_day_records에 WORKOUTS_V1을 추가해 항목별 UUID, 이름, 분, kcal, 직접 입력/복사 출처를 저장한다. 과거 데이터에 목록 키가 없으면 분리 가능한 단일 운동을 하나의 호환 행으로 보여준다. 빈 목록을 저장한 날과 목록 도입 전 날짜를 구별한다. 걷기와 운동이 섞인 과거 총열량은 ‘기존 활동 총량’으로 보존하고 임의로 분해하지 않는다.
- [ ] 활동 조회 응답에 workouts와 누락 건수를 추가한다. 새 클라이언트는 목록 및 기존 revision을 함께 저장한다. 서버는 사용자·날짜를 확인하고 목록과 합계를 한 트랜잭션에서 갱신한다. 동일 UUID 중복을 거부하고, 재시도는 동일 결과로 처리한다. 오래된 화면의 단일 운동 쓰기로 이미 저장된 여러 운동이 사라질 수 있는 경우 409와 새로고침 안내를 반환한다.
- [ ] 운동 합계에는 입력된 값만 더한다. 전부 미입력이면 null, 직접 입력한 0은 0이다. 예를 들어 웨이트 50분·250 kcal와 러닝 20분·열량 미입력은 ‘운동 2회 · 70분 · 입력 열량 250 kcal (1건 미입력)’이다. 걷기 추정은 하루 합계에 한 번만 반영한다. 기존의 운동 중 걸음 중복 입력 안내도 유지한다.
- [ ] ‘어제 운동 가져오기’는 원하는 행만 선택해 오늘의 새 항목으로 복사한다. 재시도 중복과 원본 변경을 막는다. 평균 채우기는 날짜별 추정 합계로 유지하고 실제 운동 횟수에 포함하지 않는다. 직접 운동 입력으로 대체할 때 추정값이 합계에 남지 않게 한다. 주간 운동 횟수는 하루 두 운동을 2회로 센다.

## 2. 서버에서 평가 근거 계산

- [ ] 분석 결과 저장 시점의 섭취 목표, 분석에 반영한 음식 ID와 분량, 끼니 합계, 레시피, 평균 추정, 운동·걸음 출처를 고정한다. 기존 ANALYSIS와 FOODS_V1 검증을 통과한 숫자를 재사용한다. 화면의 하루 합계와 동일한 집계 경로를 사용하고 레시피와 운동 열량을 중복 가산하거나 섭취 목표에서 임의로 빼지 않는다.
- [ ] 하루 후보는 목표와 기록 섭취량의 kcal 차이, 확인 가능한 끼니 비중, 같은 끼니의 평소 대비 변화다. 과거 비교 기본값은 직전 28일의 같은 끼니 3일 이상이며 당일·평균 채우기·불완전한 소계는 제외한다. 비교 문장에는 표본 수를 표시한다. 목표 초과는 기록한 수치로 확인할 수 있고, 목표 미만은 추가 섭취가 가능하므로 ‘기록 기준’으로 표현한다.
- [ ] 끼니 후보는 열량 기여가 가장 큰 음식, 단백질 기여 음식, 입력된 분량에 따른 산술 차이다. 일부 음식만 검증됐으면 끼니 전체의 1위라고 단정하지 않는다. 조각·그램 등 실제 양과 단위를 확보한 경우에만 분량 차이를 말한다. 추정량에는 ‘약’을 붙인다.
- [ ] 하루 한 끼만 기록하면 ‘오늘 분석에는 저녁만 포함됐어요’처럼 범위를 먼저 알려준다. 평균 채우기만 있는 끼니는 추정 소계만 보여준다. 운동 열량 일부가 비었으면 ‘입력된 운동 열량’까지만 말한다. 미입력, 추정, 실제 0을 구별한다.

## 3. 평가 생성과 문장 품질

- [ ] 기존 Gemini 요청 한 번에서 영양 추정과 함께 선택 가능한 관찰 유형과 참조할 끼니·음식 ID를 제안받는다. 최종 숫자는 응답 검증 후에 확정되므로 서버가 관찰의 성립 조건을 다시 검사하고 실제 값으로 한국어 문장을 완성한다. 추가 모델 호출 없이 근거가 부족한 제안만 제외한다. 제안이 없거나 잘못되어도 검증된 후보로 요약하고 정상 영양 분석은 저장한다.
- [ ] 하루에는 관찰 한 가지를 1~2문장으로, 기록된 끼니마다 서로 다른 정보 한 가지를 한 문장으로 보여준다. 우선순위는 기록 범위의 제약 → 충분한 비교 자료가 있는 변화 → 음식 기여도 → 단순 합계다. 같은 사실을 하루와 끼니 양쪽에서 반복하지 않는다. 분량 조절 제안은 근거가 있을 때 최대 한 번으로 제한한다.
- [ ] ‘활발히 소모했으나’, ‘나쁜 음식’, ‘운동으로 만회’, ‘내일 굶기’처럼 운동과 식사를 상벌 관계로 표현하는 문장을 피한다. 음식 이름만으로 염분·혈당·질병 위험을 추론하지 않는다. 목표 초과 원인을 특정 메뉴 탓으로 단정하지 않는다.
- [ ] 분석 성공 트랜잭션에서 FEEDBACK_V1에 하루 문장, 끼니별 문장, 사용한 근거와 입력 버전을 저장한다. 메인 분석 후 새 입력에는 ‘지난 분석 기준’을 표시한다. 추가 분석 성공 시 전체 교체하고 실패하면 직전 성공 결과를 보존한다. 활동만 수정해도 현재 활동 합계는 즉시 갱신하고, 기존 평가가 활동을 인용했다면 분석 시점 기준으로 표시한다. 과거 기록은 기존 review를 계속 읽는다.

## 4. 화면·배포·검증

- [ ] GET /meal-days/{day}에 선택 필드로 하루/끼니별 평가를 추가한다. 식사 탭에는 하루 섭취량 아래 요약을, 펼친 끼니에는 음식 목록과 함께 해당 코멘트를 둔다. 홈에서는 하루 요약만 사용한다. 날짜 조회와 펼치기는 저장 결과만 읽는다.
- [ ] 주요 변경 위치는 백엔드의 DietaService, DietaActivityHistory, DietaQuickMeals, GeminiMealClient와 분석 DTO, 프런트의 DietaActivityPage, DietaMealDetails, DietaHomePage, dietaApi 및 매퍼다. 운동 집계와 평가 후보 선정은 각각 독립적인 순수 함수로 테스트한다.
- [ ] 운동 테스트는 2건 합산, kcal 일부/전부 누락, 0분, 마지막 운동 삭제, 어제 일부 복사, 평균 대체, 구버전 쓰기와 동시 수정까지 포함한다. 평가 테스트는 단일 끼니, 평균만 있는 날, 분량 없는 음식, 과거 비교 2일/3일 경계, 무효 모델 참조, 추가 분석 실패, 과거 review 호환과 실제 모델 호출 횟수를 확인한다.
- [ ] 390px 모바일에서 운동 2개 추가 → 한 항목 수정 → 다음 날 하나만 가져오기, 하루 평가 → 끼니 평가 → 새 입력 후 이전 평가 표시를 검증한다. 백엔드 호환 응답을 먼저 배포한 뒤 Pages를 배포한다. 기존 날짜별 JSON 저장소를 활용하므로 이 설계 기준 신규 테이블이나 필수 SQL 마이그레이션은 없다.
