# Dieta 하루 식사 예약 분석 구현 계획

사용자가 설정한 시각에 웹을 열지 않아도 서버가 그날의 한 줄 식사를 모아 메인 분석을 실행한다. 사용자·식사 날짜별로 메인 1회와, 메인 성공 후 새 음식을 입력한 경우에만 수동 추가 분석 1회를 제공한다. 같은 날짜의 수동 분석을 먼저 접수했다면 예약 요청을 건너뛴다. 구현은 Spring Boot 스케줄러, MySQL, 기존 Redis 식사 큐와 React 설정 화면을 사용한다. 기존 동작의 기준은 [Dieta 기능 명세](FEATURE_SPEC.md)와 현재 수동 확정 API다.

## 사용자가 경험할 동작

| 상황 | 동작 |
|---|---|
| 매일 21:30 예약, 오늘 미분석 음식 있음 | 사용자 시간대의 21:30이 되면 당일 큐 전체를 기존 분석기로 보낸다. 21:30은 요청 시작 기준이며 혼잡 시 순서대로 처리한다. |
| 20:00에 수동 분석 성공 | 21:30 예약은 Gemini 호출 0회. 사용자가 이미 받은 결과를 그대로 표시한다. |
| 21:29에 수동 분석을 접수했고 아직 처리 중이거나 실패 | 자동 요청을 건너뛴다. 실패는 아래 전송 기준에 따라 재시도 가능 여부를 표시한다. 빈 큐나 동의 누락으로 **접수 전에 거절된** 클릭은 예약을 취소하지 않는다. |
| 예약이 먼저 실행된 직후 사용자가 버튼을 누름 | 처리 중이면 기존 진행 상태를 표시하고, 완료됐다면 저장된 결과를 돌려준다. |
| 등록 레시피만 섭취했거나 한 줄 식사가 없음 | 이미 계산된 레시피 영양값은 유지한다. Gemini 호출 없이 그날 예약을 마친다. 이후 추가한 한 줄 식사는 수동 확정할 수 있다. |

**정책 제안.** 기존 사용자의 예약은 기본 꺼짐이다. 활성화할 때 현지 시각과 시간대(예: 21:30, Asia/Seoul)를 함께 저장한다. 예약의 대상은 해당 시각이 속한 **현지 날짜**다. 예를 들어 00:10은 새 날짜의 식사를 뜻한다. 오늘 시각이 지난 뒤 예약을 켜거나 시간을 바꾸면 다음 예정 시각부터 적용한다. 메인 성공 뒤에는 새 한 줄 식사를 여러 건 모을 수 있다. 추가 분석이 마지막 기회임을 실행 버튼 옆에 안내한다.

## 메인과 추가 분석의 경계

예를 들어 19시에 밥과 닭가슴살을 수동 분석하고 20시에 사과를 기록하면, 21시 예약은 건너뛴다. 사용자가 ‘추가 음식 포함해 다시 분석’을 누르면 밥·닭가슴살·사과 전체를 한 번 보내고 그 결과로 기존 한 줄 식사의 영양 합계를 교체한다. 새로 입력한 사과를 삭제했다면 버튼은 다시 비활성화한다.

| 단계 | 입력과 호출 규칙 |
|---|---|
| 메인 실행 전 | 수동·예약·전날 자동 마감이 메인 1회를 공유한다. 빈 입력, 동의 거절, 중복 클릭은 차감하지 않는다. |
| 메인 성공 | 분석한 항목은 고정하고 새 항목만 추가·삭제할 수 있다. 메인 이후 생성되어 현재 남아 있는 새 한 줄 식사가 1개 이상일 때만 수동 추가 분석을 허용한다. 레시피·활동·설정만 변경한 경우에는 열지 않는다. |
| 분석 진행 중 | 전송할 항목을 고정하고 한 줄 식사 변경을 잠근다. 여러 탭에서 같은 요청을 보내도 진행 중 상태나 저장된 결과를 반환한다. |
| 추가 분석 성공 | 당일 결과와 리뷰를 교체하고 한 줄 식사 입력을 마감한다. 등록 레시피의 확정 영양값은 기존 방식대로 한 번만 합산한다. |

**실패 시 횟수 처리 제안.** 반복 호출과 비용을 제한하기 위해 성공 횟수가 아닌 **외부 전송 기준**으로 각 단계를 최대 1회 허용한다. 외부 전송 전 검증·준비 실패가 확인되면 같은 단계를 수동 재시도할 수 있다. 전송 개시를 DB에 기록한 뒤에는 402·타임아웃·응답 유실에도 해당 기회를 사용한 것으로 처리한다. 이 보수적인 기준에서는 전송 표시 직후 서버가 종료되면 실제 호출이 없었어도 기회를 잃을 수 있다. 메인 결과가 없으면 추가 분석을 열지 않고, 추가 분석 실패 시에는 메인 결과를 유지하면서 새 항목을 ‘분석에 미반영’으로 표시한다.

## 현재 코드와 연결할 지점

- `DietaMealsPage.tsx`는 진입 시 전날 자동 마감 API를 호출한다. 버튼의 당일 수동 확정은 `DietaController` → `DietaService.finalizeMealDay(email, loggedOn)`으로 들어간다. 기존 전날 마감은 예약을 사용하지 않는 사용자에게 유지한다.
- `DietaService`는 사용자 프로필 잠금 안에서 Redis 큐를 선점하고, 잠금 밖에서 Gemini를 호출한 뒤 다시 잠가 섭취 결과를 저장한다. MySQL의 `sourceMealsJson.queueTotals`가 완료 근거다. Redis 큐 TTL 48시간과 기존 처리권 만료 120초를 유지한다. Redis의 실패 상태만으로는 누가 요청했는지 알 수 없어 수동 접수 여부는 MySQL에 남긴다.
- `SchedulingConfig`에 이미 `@EnableScheduling`이 있다. 새로운 서버 작업은 웹 로그인 세션 없이 내부 사용자 ID로 기존 분석 경로를 호출한다. 레시피 생성용 Gemini 요청은 하루 분석 접수로 집계하지 않는다.

## 구현 순서

- [ ] **1. 예약 설정과 날짜별 실행 기록 추가.** `infra/mysql/init.sql`, `infra/mysql/migrate_dieta.sql` 및 기존 DB용 `infra/mysql/migrations/`에 같은 스키마를 반영한다. `dieta_profiles`에는 예약 활성 여부(기본 false), 현지 시각, IANA 시간대, 다음 실행 시각(UTC)을 저장한다. 활성 여부와 다음 실행 시각에 복합 인덱스를 둔다. 신규 `dieta_meal_analysis_days`는 사용자·식사 날짜를 기본키로 두고 최초 수동 접수 시각, 예약 처리 결과, 처리권 토큰 및 시각을 저장한다. 날짜별 행에 메인·추가 각각의 상태와 전송 개시 시각을 독립적으로 보관한다. 기존 완료 기록의 `queueTotals`는 메인 성공으로만 해석한다. 분석 당시 원본은 기존 `sourceMealsJson.meals`를 재사용하고 새 입력에는 별도 항목 ID를 부여한다. 과거 기록에 원본이 없어 전체 재구성이 불가능하면 기존 결과를 유지하고 추가 분석을 열지 않는다.
- [ ] **2. 설정 API와 날짜 계산.** `DietaProfile`, `DietaProfilePatchRequest`, `DietaProfileResponse`, `DietaService`에 예약 설정을 연결한다. 기존 `PATCH /profile`에서 설정 필드 생략은 종전 값 유지로 처리한다. 활성화 시 AI 이용 동의, 유효한 `HH:mm`과 시간대를 검증하고, 동의 철회 시 예약도 끈다. 서버의 주입된 `Clock`으로 다음 실행 시각을 계산한다. 현지 시각 기준으로 매일 계산하고, 일광절약시간으로 누락된 시각은 전환 직후, 반복 시각은 첫 번째에 실행한다. 예약 사용자의 섭취 탭과 홈이 사용하는 오늘 날짜도 저장한 시간대로 맞춘다.
- [ ] **3. 수동·예약·전날 자동 요청의 중복 방지.** 기존 공개 수동 API는 유지하고 내부 처리에 요청 출처(MANUAL, SCHEDULED, LEGACY_AUTO)를 전달한다. 모든 진입점이 같은 프로필 잠금을 먼저 얻고 날짜별 실행 기록 → 기존 완료 근거 → 큐 상태를 함께 검사한다. 유효한 수동 요청은 외부 호출 전에 접수 시각을 커밋한다. 수동 API에는 선택적 단계(MAIN 또는 SUPPLEMENT)를 받으며 생략 시 MAIN으로 해석한다. 자동 경로는 항상 MAIN이다. 사용자·날짜·단계로 중복을 검사하고, 추가 요청에서는 메인 성공·새 항목 존재·추가 기회 미사용을 서버가 잠금 안에서 재검증한다. `currentQueue`와 `requireEditable`의 완료 판정을 단계별로 바꾼다. 메인 결과와 추가 입력을 함께 조회하고, 추가 성공 시 `withQueueFinalize`로 전체 입력·합계·리뷰를 교체한 뒤 해당 날짜의 레시피를 다시 읽어 합산한다. 섭취 결과 교체와 추가 성공 표시는 같은 DB 트랜잭션에 커밋한다. 예약과 전날 자동 경로는 수동 접수 또는 이미 처리한 예약이 있으면 스킵한다. 예약 사용자의 화면 진입 자동 호출은 서버에서도 차단해 구버전 화면이 실행돼도 우회하지 못하게 한다. 화면의 ‘어제 분석 다시 시도’는 전송 전 실패로 재시도 가능한 경우에만 해당 날짜의 수동 MAIN API를 사용한다.
- [ ] **4. 예약 실행기와 복구.** 신규 `DietaMealAnalysisScheduler`가 1분마다 기한이 된 프로필을 인덱스로 소량 조회한다. 사용자별 잠금 안에서 현재 설정·동의·예정 시각을 다시 검사하고 해당 날짜 처리권과 다음 실행 시각을 한 트랜잭션에 저장한다. Redis 선점과 MySQL 사이의 부분 실패는 MySQL의 처리권을 기준으로 복구한다. 선점이 커밋된 작업만 제한된 수의 워커가 실행하며, 실제 전송 직전에 소유권과 동의를 재확인하고 해당 단계의 미전송 상태를 전송 개시로 원자적으로 바꾼 워커만 한 번 호출한다. 처리권 만료로 전송 표식을 초기화하지 않으며 HTTP 클라이언트의 자동 POST 재시도도 끈다. 성공 시 기존 섭취 결과와 실행 성공을 함께 커밋하고 Redis 완료 표시는 그 뒤 갱신한다. 처리권이 만료되면 이전 워커의 결과 반영을 거절한다.

  서버가 예약 시각에 꺼져 있었다면 복구 시 아직 큐가 남은 최근 48시간의 미처리 예약만 다룬다. 저장한 예정 시각부터 날짜순으로 진행하고 만료·빈 큐는 건너뛴다. 예약 실패(예: Gemini 402), 전송 타임아웃, 전송 여부가 불분명한 재시작은 해당 단계의 전송 표시를 보존하고 재시도 불가 사유를 표시한다. 이미 외부에 전송한 뒤 서버가 종료되면 외부 과금 여부까지 판별할 수 없으므로, 오래된 처리권만 보고 Gemini를 다시 호출하지 않는다.
- [ ] **5. 설정 및 결과 화면.** `frontend/src/pages/DietaSettingsPage.tsx`, `DietaMealsPage.tsx`, `frontend/src/api/dietaApi.ts`, `dietaMappers.ts`, Dieta 타입을 수정한다. 설정에는 ‘매일 식사 자동 분석’, 시간 입력, 적용 시간대, 다음 실행 일시를 표시한다. 식사 화면은 ‘오늘 21:30 분석 예정’, ‘직접 분석하여 오늘 예약 생략’, ‘분석 전 오류 · 다시 시도’ 또는 ‘분석 요청 실패 · 오늘 메인 기회 사용’처럼 실제 처리 결과를 보여준다. 화면을 계속 열어 둔 상태에서도 예약 시각 도달 및 탭 재진입 시 서버 상태를 갱신한다. 큐 응답에 단계별 상태, 새 항목 수, 추가 분석 가능 여부를 담는다. 서버 상태에 따라 ‘메인 분석’, ‘추가 음식 포함해 다시 분석 (마지막 1회)’, ‘오늘 분석 완료’를 표시한다. 실패 시에는 미반영 항목과 마지막 성공 결과를 구분한다.

## 인수 검증과 배포

| 검증 | 통과 기준 |
|---|---|
| 시간과 사용자 격리 | 고정 시계로 서로 다른 예약 시각·시간대의 두 사용자, 자정 경계, 시간 변경, 동의 철회, DST를 검증한다. 예정된 사용자·날짜에만 요청한다. |
| 수동 우선 및 동시성 | MySQL·Redis 통합 테스트에서 수동 성공·진행·실패 뒤 예약 호출 수가 각각 0임을 확인한다. 수동과 예약 동시 시작, 서버 두 대의 중복 스캔은 지연시킨 모의 Gemini로 총 요청 1회·섭취 저장 1건을 확인한다. |
| 추가 자격 | 메인 성공 직후, 신규 입력 후 모두 삭제, 레시피만 변경한 경우의 추가 호출은 0회. 새 항목이 남았을 때만 수동 추가 요청이 성공한다. 자동 마감은 추가 기회를 사용하지 않는다. |
| 횟수·합계 | 메인 500 kcal, 별도 레시피 100 kcal, 추가 후 전체 한 줄 식사 650 kcal이면 최종값은 750 kcal다. 추가 버튼 동시 클릭·세 번째 요청·새로고침·Redis 만료·서버 재시작 뒤에도 사용자·날짜당 Gemini 호출은 최대 2회다. 다음 날짜와 다른 사용자는 각자의 기회를 갖는다. |
| 단계별 실패 | 전송 전 거절은 차감 0회, 전송 후 실패·응답 유실은 해당 단계만 소진한다. 추가 실패 시 메인 500 kcal와 레시피 100 kcal가 남고 미반영 항목을 표시한다. |
| 기존 기능 호환 | 예약 꺼짐 상태의 전날 자동 마감, 기존 완료 기록, 레시피만 있는 날, 빈 큐, 수동 재시도, 구버전 화면의 자동 호출을 각각 검증한다. |
| 장애·복구 | 서버 정지 후 재시작, TTL 만료, Gemini 402, 응답 후 DB 커밋 전 중단, 커밋 후 Redis 갱신 실패를 주입한다. 늦은 중복 전송 및 중복 합산이 없어야 한다. |
| UI | 설정 저장·재접속, 실패 후 명시적 재시도, 열린 탭에서 예약 완료 표시를 컴포넌트 테스트와 모바일·데스크톱 브라우저로 확인한다. |

배포는 추가형 DB 마이그레이션 → 새 백엔드 전체 교체 → 프런트엔드 순서다. 기존 백엔드 인스턴스가 모두 교체된 뒤 예약을 활성화한다. 개발 환경에서는 Gemini 모의 응답으로 호출 수를 측정하고, 운영 확인은 동의한 시험 계정 한 명의 수동 선행 사례와 예약 단독 사례로 나눠 진행한다. 운영 로그에는 요청 출처·처리 결과·오류 분류를 남기고 식사 원문이나 API 키를 넣지 않는다.
