# 운영 감시와 DEV 운영 기록

## Discord 중단·복구 알림
1. 알림을 받을 Discord 채널의 **채널 설정 → 연동 → 웹후크**에서 웹후크를 만들고 URL을 복사한다.
2. GitHub 저장소의 **Settings → Secrets and variables → Actions → New repository secret**에 이름 `PBB_DISCORD_WEBHOOK_URL`로 저장한다. 앱 서버나 로컬 .env에는 넣지 않는다.
3. 기본 브랜치에 워크플로가 반영된 뒤 **Actions → PBB external uptime → Run workflow**에서 테스트 메시지 옵션을 선택한다. Discord 수신 및 Actions 성공을 확인한다.
4. GitHub-hosted 러너가 약 5분마다 웹 루트와 API의 Actuator health를 별도로 확인한다. 한 실행에서 10초 간격으로 3번 실패한 대상에 중단 알림을 보내며, 다시 정상 응답하면 복구를 알린다. 전체 앱이 내려가도 이 작업은 독립적으로 실행된다.

Actions가 비활성화되거나 실행 할당량이 소진되면 감시도 중단된다. 예약 시각은 정확히 보장되지 않는다. 마지막 전달 상태(API/웹 이름만)는 Actions 캐시에 저장한다. Discord 전송 실패 시 상태를 갱신하지 않아 다음 점검에서도 상태 차이가 지속되면 재시도한다. 캐시 유실이나 저장 실패 시 중단이 중복 통지되거나 복구를 놓칠 수 있다. 점검 사이에 끝난 짧은 장애도 감지되지 않을 수 있다.

## DEV 운영 기록
- 운영 배포 전 대상 DB에 `infra/mysql/migrations/20261113_dev_operations.sql`을 먼저 적용한다. 기존 테이블이나 행을 변경하지 않는다. dev에서는 같은 SQL이 Flyway로 실행된다.
- DEV 계정의 **프로필 → 오늘의 운영 기록**에서 서울 날짜 기준으로 앱을 선택한다. Spring MVC 앱 API가 반환한 5xx를 기능·상태별로 합산한다. 최근 요청 ID로 Spring의 `operation_failure` 로그를 검색할 수 있다. 웹 브라우저 내부 예외, 백그라운드 작업, Spring까지 도달하지 못한 요청은 이 집계에 포함되지 않는다. DB가 중단되면 집계가 누락될 수 있다.
- 회원 등급과 메인 추천 앱 목록의 실제 변경은 관리자 UUID, 대상, 변경 전후 값을 같은 DB 트랜잭션에 기록한다. 무변경과 롤백은 이력에 남지 않는다. 이력에서 이메일·토큰·사용자가 입력한 검색어나 원본 요청은 노출하지 않는다.
- 서울 시간 매일 03:25에 오류 집계는 최근 30일, 감사 이력은 최근 90일만 남긴다. 오늘 기록은 새로고침하여 확인한다. 변경 이력은 최근순 30개 단위로 조회한다.
